# Сценарий проверки этапа 1

Сценарий проверяет, что исправления этапа 1 ([план](../SECURITY-REMEDIATION-PLAN.md), раздел «Этапы работ») действительно работают. Его может выполнить ИИ-агент без участия человека: все шаги — команды, у каждой проверки есть статус и критерий.

> Отчёт описывает уязвимости. Не публикуйте его и не отправляйте в публичные репозитории.

## Что проверяется

| Поток | Проверка |
|---|---|
| Э1-1 | Нет встроенных адресов телеметрии. Телеметрия включается только явно. `1/true/yes/on` в `DO_NOT_TRACK` и `PAPERCLIP_TELEMETRY_DISABLED` её отключают. Без адреса сборщика сетевых запросов нет. Выгрузка feedback выключена без явного URL |
| Э1-2 | Нет запуска процессов через shell. Лаунчер pnpm передаёт `&`, `\|`, `^` как один аргумент. CLI на Windows открывает URL через `rundll32`, а не через `cmd`, и отклоняет опасные URL |
| Э1-3 | Smoke-образы запускаются не от root (статически, через Trivy и сборкой образа) |
| Э1-4 | В compose нет опубликованного порта Postgres и пароля по умолчанию. В `.env.example` и документации нет `paperclip:paperclip@` |
| Э1-5 … Э1-7 | Базовая проверка безопасности: нет `Math.random`, MD5/SHA-1 (кроме протокольных), shell, адресов телеметрии. Тесты на замену |
| Э1-8 | Редиректы: полезные нагрузки `//evil`, `https://evil`, `/\evil`, `javascript:` не доходят до `res.redirect`. Тесты ограничения регистрации OAuth-клиентов |
| Э1-9 | Раздача UI плагинов не отдаёт скрытые файлы; экранирование OAuth-страницы |
| Э1-10 | `@grpc/grpc-js` не ниже 1.14.5; решение по `hyper` помечено как открытое |
| Э1-11 | Необязательно: повторный прогон Horusec (около часа) для сравнения с реестром |

## Что нужно заранее

- Ветка этапа 1 (`pilot/hardening`) выгружена в рабочий каталог с установленными зависимостями (`pnpm install`).
- Node.js 24 и `pnpm`.
- Для проверок образов и compose: запущенный Docker. Trivy необязателен: без него проверка помечается `SKIP`.
- Сценарий ничего не меняет в проверяемом репозитории. Он читает файлы, запускает тесты и пробы, пишет отчёт в свою папку `results/`.

Сценарий лежит в ветке `infosec-comments`, а код — в `pilot/hardening`. Проверяйте код любым из способов:

```bash
# 1. Рядом лежит копия кода этапа 1 (в ней уже есть node_modules)
node infosec-comments/stage1-verification/run.mjs --repo /путь/к/pilot-hardening --with-docker

# 2. Код этапа 1 в текущем каталоге (скрипт взят из ветки infosec-comments)
node infosec-comments/stage1-verification/run.mjs --with-docker
```

## Шаги для агента

1. Убедитесь, что код этапа 1 выгружен и зависимости установлены:

   ```bash
   git -C <репозиторий> rev-parse --abbrev-ref HEAD   # ожидается pilot/hardening
   test -d <репозиторий>/node_modules && echo ok
   ```

2. Запустите быструю проверку (несколько минут):

   ```bash
   node infosec-comments/stage1-verification/run.mjs --repo <репозиторий>
   ```

3. Если запущен Docker, добавьте `--with-docker`: проверки образов и compose, а не только текст файлов.
4. Откройте `results/<время>/report.md`. Код выхода `0` означает, что ни одна проверка не провалена.
5. Для каждой строки `FAIL` не исправляйте код сами. Приведите команду, вывод и файл со строкой из отчёта, чтобы разработчик поправил этап 1.
6. Строки `OPEN` — известный остаток работ, это не провал. Перечислите их в итоге.
7. Необязательно: `--with-scanners` запускает Horusec в Docker (около часа). Затем сравните число срабатываний со столбцом «Происхождение» в [stage1-registry.csv](../stage1-registry.csv) скриптом `compare.py` из `reports/stage1`.

## Как читать статусы

| Статус | Значение |
|---|---|
| `PASS` | Критерий выполнен |
| `FAIL` | Критерий не выполнен. Блокирует передачу этапа 1 в ИБ |
| `OPEN` | Известный остаток. Не провал, но передавать в ИБ нужно вместе с пояснением |
| `SKIP` | Проверка не запускалась (нет Docker, нет Trivy, нет ключа) |
| `INFO` | Сведения для решения человека |

## Известный остаток

- **`passwords.embedded`**. Встроенная БД для разработки по-прежнему создаётся с паролем `paperclip` и слушает только `127.0.0.1`. Нужен случайный пароль при инициализации с переносом уже созданных кластеров. Это затрагивает около 15 файлов, где собирается строка подключения.
- **`deps.hyper`**. Совпадение `hyper 1.11.1` с CVE-2024-23741 похоже на ложное: CVE относится к терминалу Hyper. Подтвердить с командой безопасной разработки и зафиксировать в Dependency-Track.
- **`hash.exceptions`**. Остались протокольные алгоритмы: SHA-1 в `Sec-WebSocket-Accept` (RFC 6455) и UUIDv5 (RFC 9562), MD5 в S3 `Content-MD5`. Нужна заявка в службу ИБ на исключение.
- Тесты `server/src/__tests__/plugin-ui-static.test.ts` («serves built UI assets publicly…») на медленной машине падают по тайм-ауту 15 с и на чистой ветке `master`. Сценарий запускает vitest с тайм-аутом 90 с.

## Критерии передачи в ИБ

Этап 1 готов к передаче, если одновременно выполнено:

1. `run.mjs --with-docker` завершился с кодом `0`.
2. Строки `OPEN` объяснены в сопроводительном письме.
3. Код прошёл CI на том же коммите (`pnpm verify` локально требует широкой проверки в CI: изменён `README.md`, глобальный вход CI).
4. Повторный прогон Semgrep и Horusec теми же конфигурациями показывает снижение по Э1-6 (слабый ГСЧ), Э1-7 (MD5), Э1-2 (shell) до нуля либо до согласованных исключений.
